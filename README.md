# Cutaway

**Take things apart. Find out how they work.**

An offline-first Android app for exploring the inside of manufactured objects in
3D — rotate them, blow them apart, cut through them, tap any part to learn what
it does, then take a quiz on it. Anatomy, but for everything humans build.

Three objects ship as a working prototype: a **smartphone**, a **high-bypass
turbofan**, and a **single-cylinder four-stroke engine**.

---

## The one idea that matters

**Parts are identified by mesh name in the `.glb`, not by coordinates in a
content file.**

Everything an interaction needs is derived from the geometry at load time:

| Feature | Derived from |
|---|---|
| Hotspot anchor | Part's bounding-box centre, floated toward the camera |
| Tap target | Raycast against the part's own meshes |
| Explode direction | Author's vector, else radial from the object's centre |
| Camera framing | Object's world half-extents vs. the screen's two field-of-view angles |
| Isolate / peel / x-ray | Per-part cloned materials |
| Parts list | The same part list, grouped by `layer` |

Adding an object is therefore **one `.glb` with named meshes plus one JSON of
prose**. There are no 3D coordinates to hand-tune, which is the thing that stops
a library like this scaling past a dozen objects with one developer.

## Adding an object

> Two recipes carry the detail: [docs/authoring-an-organ.md](docs/authoring-an-organ.md)
> and [docs/authoring-a-machine.md](docs/authoring-a-machine.md). Read the one
> that fits before writing geometry — between them they hold every trap that
> cost a rebuild to find, and the rules genuinely invert between the two.


1. **Model it.** Any tool that exports glTF. One mesh per part, named — that
   name is the contract. Keep it under ~40k triangles.
   Drop it in `assets/models/<name>.glb`, where `<name>` is **lowercase letters,
   digits and underscores only** — the file is embedded as an Android resource
   and hyphens are illegal there. `npm run validate` enforces this, because the
   failure otherwise surfaces much later as an opaque prebuild error.
2. **Describe it.** Copy `content/smartphone.json` to `content/<id>.json`.
3. **Register it.** Add one row to `src/content/registry.ts` (Metro needs a
   static `require` to bundle an asset).
4. **Check it.** `npm run check` — this fails loudly if the JSON names a mesh
   the model does not have, and warns about meshes the JSON forgot.

No app code changes. Ever.

### The content schema

See `src/content/types.ts` for the full typed contract. The parts that need
explaining:

```jsonc
{
  "cutAxis": "x",              // which way the cross-section plane slices
  "restRotation": [0.12, -0.5, 0],   // how the object presents itself at rest
  "parts": [{
    "nodes": ["display", "display_flex"],  // mesh names in the .glb
    "layer": 0,                // 0 = outer shell, higher = deeper in. Drives peel.
    "explode": [0, 0, 1.1],    // optional; normalised units (object fits a 3.4 cube)
    "motion": {                // optional; all terms are zero at cycle 0
      "spin":  { "axis": "y", "ratio": 1 },     // ratio is per crank revolution
      "slide": { "axis": "y", "amplitude": 0.31, "phase": 0 },
      "swing": { "axis": "z", "amplitude": 0.3 }
    }
  }]
}
```

**Motion axes are in the model's own coordinate system** — the same space the
mesh was authored in — and rotations happen about the part's own bounding-box
centre, so a crankshaft spins about its journal rather than about the origin.

Every motion term is zero at cycle 0. That makes the authored pose the rest
pose, so pressing **Run** starts from exactly where the model was sitting
instead of snapping to some point mid-cycle.

## Running it

```bash
npm install
npm run build:models   # regenerates the prototype .glb files
npm run check          # typecheck + content validation + engine smoke test
npm run android        # debug build onto a connected device or emulator
```

`npm run web` also works and is the fastest way to preview a model change
without a native rebuild.

For a release APK — bundled JS, embedded assets, no Metro — use the canonical version-checked production path:

```bash
npm run build:apk -- 0.13.0
```

That command rebuilds generated assets, synchronizes the ignored Android project, assembles only ARM64, and runs the complete release verifier. See "Building a production APK" below for its guarantees and output path.

Two Windows-specific notes, both of which cost time here:

- `ANDROID_HOME` must be set, or `android/local.properties` must contain
  `sdk.dir=C:/Android/Sdk`. **Use forward slashes.** A backslash path in a Java
  properties file is read as escape sequences and silently resolves to
  nonsense — the resulting Gradle error is `The filename, directory name, or
  volume label syntax is incorrect`, which points nowhere near the cause.
- `android/` and `ios/` are gitignored. They are generated by prebuild, so
  never edit them directly — change `app.json` and regenerate.

## Architecture

```
app/                      expo-router screens
  index.tsx                 library
  object/[id].tsx           explorer  — the 3D screen
  quiz/[id].tsx             quiz
src/
  engine/                 three.js. Zero React.
    CutawayViewer.ts        scene, render loop, every tool
    Assembly.ts             the object, indexed by part
    OrbitCamera.ts          spherical camera driven by gesture deltas
    Hotspots.ts             the labelled dots
    AssetManager.ts         bundled .glb loading + LRU
    textures.ts             every texture, generated from arithmetic
    RenderScale.ts          draws the scene below screen resolution
    renderer.ts             expo-gl → three.js bridge
    polyfills.ts            TextDecoder, which Hermes does not ship
  content/                schema + library index
  ui/                     components, theme, the gesture surface
  state/progress.ts       what has been visited and scored
  state/settings.ts       theme choice
content/*.json            one file per object
tools/                    model generator, validator, smoke test
```

### React and three.js never touch

`src/ui/Viewport.tsx` is the entire boundary. React calls imperative methods on
the viewer and gets selection changes back through callbacks. A spinning model
never causes a React render, and a React render never costs a frame.

### The render loop draws only when something changed

Every mutation marks the scene dirty; tools that animate hold it dirty for a
known duration. A still, unselected object costs nothing per frame — which on a
phone is the difference between an app you can browse for twenty minutes and one
that gets warm in two.

### Mobile performance decisions

- **No shadow maps.** A baked contact-shadow quad reads the same and avoids
  rendering every part a second time each frame.
- **No HDR environment.** A 32×16 gradient, PMREM-baked once per theme, gives
  metals something to reflect. Zero bytes in the APK. The object's accent
  reaches the model through the rim light, which is what ties it to its card in
  the library.
- **No canvas.** React Native has none; every texture is written into a typed
  array in under a millisecond.
- **One mesh, one material per part.** Keeps draw calls at part-count.
- **Only the Ionicons font ships.** Importing from `@expo/vector-icons` directly
  pulls in ~3.5 MB of icon fonts; the per-family subpath import pulls 390 KB.
- **The scene renders below screen resolution** and is stretched over it. See
  `RenderScale.ts` — this one is not a nicety, it is what stopped an
  entry-level phone from killing the app outright.
- **No MSAA above a small pixel budget**, and back faces are culled except
  while a cross-section is open.
- **The environment map is baked once per theme**, not per object. It used to
  be rebuilt on every load, tinted by that object's accent — a GPU stall
  landing exactly when the user had just opened something and started dragging.
  The accent reaches the model through the rim light instead.
- **Frame pacing only engages when the device cannot cope.** If a frame costs
  more than 20 ms the loop holds to 30 Hz rather than letting frames queue.
  A device rendering in 3 ms never notices it exists.

### Two themes

`useColors()` supplies the palette; `StyleSheet.create` keeps only what does not
change, because styles built at module scope capture their values once. The 3D
stage switches too — background, fog, light intensities and the environment map
— since a light stage is not a dark one with the background swapped. With a
bright surround, bounced light does most of the work, so the directional rig has
to come down or every surface blows out.

## Verification

`npm run check` runs three gates, none of which need a device:

1. **`tsc --noEmit`** — the app is strict TypeScript.
2. **`tools/validate-content.mjs`** — reads mesh names straight out of each
   GLB's JSON chunk and checks every part, step and quiz question against them.
   A JSON that names a mesh the model lacks is the one failure mode this project
   is genuinely exposed to, and it would otherwise be silent.
3. **`tools/smoke-test.mts`** — builds a real `Assembly` from each real `.glb`
   and asserts the invariants: parts resolve, normalisation lands in the fit
   cube, exploding grows the object and collapsing returns it exactly, cycle 0
   is the rest pose, a 1:1 spinner returns to zero after one revolution, ghosted
   parts stop writing depth, clipping reaches every material, and a ray through
   every part's centre hits geometry.

The smoke test earns its keep: it caught the motion phase bug and the framing
bug during development, and it now also holds two rules that were shipped
backwards and could not be seen by reading the code:

- **A positive lift raises the subject on screen.** The lift exists to slide the
  model out from behind the narration sheet. Raising the look-at point does the
  opposite — whatever the camera looks at is what sits at the centre — so the
  first version pushed the model further *into* the sheet it was escaping. The
  test settles the easing and projects the origin to check which way it went.
- **Focusing removes what is in front of the focus.** Ghosting everything else
  reads fine for a part near the surface and not at all for one buried inside:
  half a dozen translucent shells stacked in front of the core still veil it, so
  "focus the core" left the core no easier to see. Anything shallower than the
  focused set is now removed outright. The rule lives in `src/engine/visibility.ts`
  as a pure function precisely so it can be checked without a GPU.

### Verified on device

A release APK was built and driven by hand on an emulator (API 36) and on a
**Redmi Note 11 — Snapdragon 680, Adreno 610, 1080×2400**: library, model load,
render, framing, orbit and auto-rotate, tap-to-select landing on the right part,
the part sheet with its ghosting of everything else, the explode slider across
all 13 parts of the turbofan, the parts index, the walkthrough, the quiz, and
both themes. Screenshots in `.shots/`.

**The phone was where the real defect was.** It crashed within seconds of
opening an object, and only there — the emulator survived a stress script that
flung the model around 28 times per load, eight loads running. The log said why:

```
QueueBufferDuration = 1.11 s          the GPU cannot finish a frame
Davey! duration=2731ms
Adreno-GSL: IOCTL_KGSL_GPU_COMMAND failed: errno 35 Resource deadlock
Process com.cutaway.explorer has died
```

Frames queued until the Adreno driver refused further submissions and the
process was killed. Dragging made it worse only because dragging forces a render
on every vsync. The fix had to be a real reduction in GPU work, which is what
`RenderScale`, the MSAA budget, backface culling and the pacing guard are.

Five things only a device found, none of which any headless check could have:

1. **three.js r163 dropped WebGL 1**, and guards it with
   `context instanceof WebGLRenderingContext`. expo-gl's context is GLES3-backed
   and exposes the full WebGL 2 API, but its class descends from the global
   that expo-gl installs, so the guard misfires and the renderer refuses to
   start. `src/engine/renderer.ts` hides that global for the length of the
   constructor, gated on the context actually having WebGL 2 entry points.
2. **A failure in `Viewport` was swallowed.** It set local state that rendered
   an opaque black rectangle and told the screen above nothing, so the parent
   sat on "loading" forever. A renderer that cannot start looked exactly like a
   slow model. That, not the WebGL problem, is why this took so long to find:
   the app had no way to tell anyone what was wrong.
3. **`piston-engine.glb` was an illegal Android resource name.** Hyphens are not
   allowed. `npm run validate` now enforces the character set.
4. **Hotspots were sized in raw pixels**, which is right on a 1× screen and a
   speck on a 3× phone. They are now sized in points and scaled by the density
   the gesture layer measures.
5. **The scene was simply too expensive** for an entry-level GPU at native
   resolution — see above. Nothing about this is visible on a desktop.

A caution worth recording: two of the theories chased along the way were wrong
(the asset URI, and the PMREM bake throwing), and one apparent bug — a model
rendering almost black — turned out to be the emulator's own "System UI isn't
responding" dialog dimming the whole screen, screenshot included. Measure before
concluding; a screenshot is evidence about the screen, not about the renderer.

### The APK can ship models you did not build

Gradle decides for itself whether its bundling task needs to run, and it gets
this wrong. Rebuilt `.glb` files were packaged from a previous run's copies
**twice in a row**: the APK came out four bytes different from the last one, and
two rounds of "the model is fixed" reached a phone still running the old
geometry. `npm run check` had nothing to say, because it validates the sources
and not the artefact.

Always build with:

```bash
npm run build:apk -- 0.13.0
```

The optional argument must match `expo.version` in `app.json`; omitting it uses
that version. The command rebuilds the models and brand, runs the full source
contract, synchronizes the ignored native project with Expo prebuild, and then
forces an ARM64 release bundle with Gradle's task and build caches disabled. It
does not delete generated directories or run a native clean.

The result is always `dist/cutaway-<app-version>-arm64.apk`. Before accepting
it, `tools/verify-apk.mjs` proves the current package/version/code, valid APK
signature, arm64-only native libraries, the exact 28 Metro model assets plus
the exact 28 AAPT model resources, all 28 unique object icons, and every current
launcher/adaptive/splash density derived from `app.json`. Configure an Android
SDK through `ANDROID_SDK_ROOT`, `ANDROID_HOME`, or `android/local.properties`.
A newer timestamp on the APK proves nothing; the stale one had that too.

### Looking at a model before it ships

`npm run preview` serves the repo and `tools/preview.html` renders any built
`.glb` with the app's exact stage — same environment bake, same five lights,
same intensities. Open `http://localhost:5179/?model=heart`, or drive it from
outside with `window.capture()`, which renders each view and posts it to the
server to be written into `tools/shots/`. That last path exists because the
models are built headlessly and then shipped into an APK: without it, the first
time anyone sees a surface is on a phone, which is a bad place to discover that
an organ reads as a balloon.

Three defects in the heart came straight out of looking at it:

- **The grooves were buried inside the muscle.** They had been authored by hand
  at the radius of the chambers rather than the radius of the skin, so the
  trench, the fat and every coronary artery sat a couple of centimetres under
  the surface where none of it was visible. They are now all derived from one
  description of the outer surface and cannot drift apart again.
- **A hard crease ran down the front.** `part()` recomputes normals on a
  non-indexed mesh, which throws away the seam normals `LatheGeometry` had
  already got right: two coincident vertices with no index in common each
  average only their own side's faces. Invisible on a machined part, and on an
  organ it made the two halves read as flat panels hinged together. `geo.mjs`
  now exports `smoothSeams()` for surfaces that want welding before shading —
  opt-in, because welding also rounds off every deliberate hard edge.
- **The pericardium hid the whole organ**, and the first three fixes were all
  the same mistake — cutting geometry to solve a rendering problem. Closed, it
  opened as a smooth white egg. Opened at the front, it still covered the entire
  back and became a dark blanket the moment auto-rotate came round. Reduced to a
  collar, it read as a helmet sitting on top of the heart, which was the worst of
  the three because by then it was teaching something false. It is now whole,
  with a resting `opacity` in the content — see `Part.opacity` and
  `src/engine/visibility.ts`. A part that genuinely encloses everything else
  needs to be see-through, not reshaped.
- **The preview was rendering a view that exists nowhere in the app.** It loaded
  the raw `.glb` and framed it from a camera of its own, while the app applies
  each object's `restRotation` and opens on the explorer's default orbit. That
  is why the pericardium passed inspection as a thin rim and arrived on the
  phone as a blanket. `tools/preview.html` now applies both, and its `app` view
  is the one that counts.

### What is still not covered

Automated coverage of the GL path — every check on it so far has been a human
looking at a screenshot. `tools/device-check.sh` scripts the walkthrough and
captures shots at each step, but nothing asserts on them.

**It has only run on an emulator, never on physical hardware.** The emulator's
GL driver is not a real one; test on an actual phone before shipping. Two
things to watch there specifically: whether the environment-map bake succeeds
(it is non-fatal either way, but reflections depend on it), and sustained frame
rate with the animation running.

## Known limitations

- **No image textures, anywhere.** `GLTFLoader` needs `createImageBitmap` for
  glTF images, which React Native does not provide, so a `.glb` that references
  one will not load at all. Surface variation therefore comes from per-vertex
  colour, which does survive the round trip: `geo.mjs` has `displace()`,
  `paint()` and `srgb()`, and the heart uses them for its mottling, the dark in
  the grooves and the epicardial fat. Note that `COLOR_0` is *linear* data while
  every colour a person picks is sRGB — writing the sRGB numbers straight in
  washes the result out badly, which is what `srgb()` is for.
- **Textured models will not load.** `GLTFLoader` needs `createImageBitmap` for
  glTF images, which React Native does not provide. The prototype models are
  untextured so this never fires. Before shipping an artist-made model with
  texture maps, wire an `expo-gl`-backed texture loader into `AssetManager`.
- **Cross-section has no cap.** Clipping is done with `DoubleSide` materials, so
  a cut reveals the inside of a wall rather than a solid face. Capping needs a
  stencil pass.
- **Prototype kinematics are approximate.** The piston engine's phases are
  visually plausible, not a true slider-crank solution. Tune the `phase` values
  once real geometry lands.
- **expo-router bundles a ~1 MB Material Symbols font** for its internal screens.
- **The render scale is a fixed pixel budget, not adaptive.** A flagship renders
  the same 1.15 MP as a budget phone and simply has headroom to spare. Raising
  it per device would need real measurement, and a badly tuned adaptive
  controller is worse than a fixed one — it oscillates.

## Play Store readiness

Done: package id `com.cutaway.explorer`, portrait lock, edge-to-edge, adaptive
icon slots, dark theme, no network permission, no ads, no tracking, all content
on-device.

**Ship an `.aab`, not the `.apk`.** `./gradlew assembleRelease` produces a
~100 MB universal APK because it carries native libraries for all four ABIs.
`./gradlew bundleRelease` produces an app bundle and Play splits it per device,
which takes the download to roughly a quarter of that. For a local install on
one device, `-PreactNativeArchitectures=x86_64` (emulator) or `arm64-v8a`
(phone) builds far faster and much smaller.

Still needed: a real app icon and feature graphic, a signing key of your own
(the release build is currently debug-signed), a privacy policy URL (the app
collects nothing, so it is short), store screenshots, and an `eas build`
configuration.
